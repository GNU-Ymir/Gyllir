Publishing

Bump the version, tag it, and push it where other packages can depend on it.

The registry

Every package declares a registry — the place its versions are published to. It takes the same two forms as a dependency URL:

[registry]
git = "git@github.com:jane/myapp.git"
[registry]
local = "/home/jane/.local/gyllir/myapp"

A registry is not a server — it is just a git remote, or a directory on your machine. Packages depend on it through their own [dependencies.*] tables, so "publishing" means making a tagged version reachable from that URL.

Publishing a version

gyllir publish "Add the frobnicate option"           # bumps the patch: 1.2.3 -> 1.2.4
gyllir publish "New API" --minor                     # 1.2.3 -> 1.3.0
gyllir publish "Breaking rewrite" --major            # 1.2.3 -> 2.0.0

The message is required — it becomes the commit message of the version. The three bump flags are mutually exclusive, and a patch bump is the default.

What it does, in order:

  1. Asks for confirmation, unless -y was given.
  2. Builds every target and runs their unit tests. If a test fails, publishing stops with that exit code. --dry skips this verification entirely.
  3. Bumps version and rewrites gyllir.toml.
  4. git add ., commits with your message, and tags the commit v<new version>.
  5. Publishes to the registry:
    • local: — the registry directory is removed and replaced by a copy of the package.
    • git: — the package is copied to a temporary directory, the registry URL is set as origin, and the new tag and the master branch are pushed.

gyllir.toml is rewritten, not patched. It is serialized from the parsed manifest, so comments and key ordering in the file are not preserved across a publish. Keep anything you care about in version control — which the publish commit does for you.

The git flow pushes the master branch. A package that publishes from another branch name needs to push it by hand.

Versions and tags

The tags are the source of truth: when another package declares a version filter, Gyllir reads the tag list of your repository and picks the highest tag that passes. So a version only becomes usable once its tag is reachable at the registry URL.

Tags may be written 1.2.0 or v1.2.0 — gyllir publish writes the v form.

Keeping a version constant in sync

If your code has to know its own version, do not maintain a second copy by hand — generate it from the manifest with a pre-build command. That is what Gyllir itself does:

[commands]
set-version = { cmd = "./tools/set-version.sh", post = false }

The script reads version out of gyllir.toml and rewrites the constant in the sources, before every build.

Publishing to a local registry

A local registry is the quickest way to try the whole loop without a remote:

[registry]
local = "/home/jane/.local/gyllir/mylib"
gyllir publish "First release" --minor -y

Another package then depends on the published copy:

[dependencies.mylib]
version = ">=0.2.0"
url = "local:/home/jane/.local/gyllir/mylib"
