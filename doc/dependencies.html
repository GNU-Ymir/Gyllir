Dependencies

Other Gyllir packages your package builds against, fetched from a git remote or a local path and built before yours.

Declaring one

One [dependencies.<name>] table per dependency. The name is yours to choose — it is the directory the dependency is resolved into, and the name targets use to select it.

[dependencies.somelib]
version = ">=1.2.0"
url = "git:https://github.com/example/somelib"

[dependencies.midgard]
version = "*"
url = "local:/home/jane/ymir/midgard"
KeyTypeRequiredDescription
versionstring or arrayyesThe version filter deciding which version is checked out.
urlstring or tableyesWhere to get it: git:<remote> or local:<path>, see URLs.
link-targetsarray of stringsnoWhich of the dependency's library targets to link. Omit to link all of them; it cannot be empty.

Version filters

FilterSelects
"*"Any version — the highest one available.
"1.2.0"Exactly that version.
">=1.2.0"The highest version at least 1.2.0. >, < and <= work the same way.
[">=1.2.0", "<2.0.0"]An array is a conjunction: every filter must pass.
"master"A name — a branch or a non-numbered tag — matched literally.

Versions come from the git tags of the dependency, and a tag may be written either 1.2.0 or v1.2.0. Among the tags that pass the filter, the highest one wins. Comparators only make sense against a numbered version: ">=master" is rejected when the manifest is read.

When no version matches, the error lists the versions the dependency actually offers, so you can see whether the filter or the remote is at fault.

How resolution works

On every build, for each dependency, Gyllir:

  1. Places it under .deps/<name> — a local: dependency becomes a symlink to the given path (recreated each time), a git: one is cloned there the first time and reused afterwards. A git: dependency whose url changed in the manifest has its checkout re-pointed at the new remote.
  2. Picks a version: if gyllir.lock already pins one that the filter still accepts, that exact commit is checked out and nothing is fetched. Otherwise, if the branch currently checked out already passes the filter, it is kept as is — that is what makes local, in-progress dependencies usable — and failing that, the tags are fetched and the matching version is checked out.
  3. Reads the dependency's own gyllir.toml and resolves its dependencies, recursively.
  4. Builds its library targets, and puts their root modules on your include path and their archives on your link line.
  5. Records what it resolved in gyllir.lock.

The lock file

gyllir.toml declares which versions are acceptable; gyllir.lock records the one that was actually resolved. Without it, a build of the same commit picks up whatever tag has been pushed upstream since — a build that is not reproducible, and an indirect dependency that can move with nothing in your repository changing.

It is written by build, run, test and doc, alongside the manifest, and looks like this:

# This file is generated by gyllir, and records the exact dependency versions the package was
# last resolved with. It is meant to be committed, and not to be edited by hand.
lock-version = 1

[[package]]
name = "somelib"
url = "git:https://github.com/example/somelib"
version = "1.4.2"
sha = "9f1c0d0a1b0e5f6d7c8b9a0f1e2d3c4b5a697887"
dependencies = ["git:https://github.com/example/core"]

[[package]]
name = "core"
url = "git:https://github.com/example/core"
version = "2.0.0"
sha = "0b1a2c3d4e5f60718293a4b5c6d7e8f901234567"
KeyDescription
lock-versionThe format of the file. A lock file written by a newer Gyllir is rejected rather than half-read.
nameThe name the package is declared under.
urlWhere the package was resolved from. An entry only applies while the manifest still declares that same url.
versionThe version that was resolved — what the filter is re-checked against on the next build.
shaThe commit that version pointed at, for a git: url. A tag can be moved, a commit cannot.
dependenciesThe urls that package depends on, which is what makes the file a graph rather than a list.

Every dependency is in there, transitively — the entry for an indirect dependency looks exactly like the one for a direct one. A local: path is recorded but never pinned to a commit: it is a working checkout of yours, not a released version, and it carries no sha.

Commit it

gyllir.lock belongs in git, next to gyllir.toml — that is the whole point: everyone building your package, on any machine, at any time, builds the same dependencies. It is deliberately sorted and one block per package, so that it reads in a code review and conflicts stay local to the entry that moved.

Moving a version

A build never bumps a pinned version, even when a newer tag exists upstream. gyllir update is what does:

gyllir update             # re-resolve everything
gyllir update somelib     # re-resolve only "somelib"

A build does re-resolve, and rewrite the file, when the lock file no longer agrees with the manifest: a dependency was added, its url changed, or its filter was narrowed past the version that was pinned.

In CI

gyllir build --locked     # fail instead of resolving anything new
gyllir build --offline    # ... and without touching the network at all

--locked turns "the lock file is out of date" into an error rather than a rewrite, which is what makes a CI run prove that the committed lock file describes the build. --offline adds to it: nothing is cloned, fetched or pulled, so every dependency has to be pinned and already present in .deps/.

A pinned commit that has disappeared from its remote — a force-pushed branch, a deleted tag — is reported as such, and named together with the gyllir update <name> that fixes it.

A dependency is checked out by version, so even a local: one has to be a git repository. If it is not, the error says so explicitly.

What gets linked

Only the library targets of a dependency are of any use to you: an executable it also declares is never linked into your package. A dependency that declares no library target at all is an error.

By default every library target of the dependency is linked. link-targets narrows that down:

[dependencies.toolkit]
version = ">=2.0.0"
url = "git:git@github.com:example/toolkit.git"
link-targets = ["core"]        # ignore the other libraries it ships

Naming a target the dependency does not declare, or one that is an executable, is an error that lists what it does declare.

On your side, each target selects which dependencies it links — and remember that a declared target links exactly the ones it lists.

Cycles

A dependency graph that comes back to a package already being resolved is rejected with a RecursiveDependency error naming the chain. The same applies to targets linking each other inside one package.

Keeping the tree clean

gyllir clean --all        # removes .deps/ as well as the build outputs

.deps/ is in the .gitignore that gyllir init writes, and should stay untracked: it is entirely reconstructible from the manifest and the lock file — which are the two files to keep.

Example: a library and its user

In ~/ymir/mylib/gyllir.toml:

name = "mylib"
license = "MIT"
description = "A small library"
version = "1.0.0"
type = "library"

[registry]
local = "/home/jane/.local/gyllir/mylib"
cd ~/ymir/mylib
gyllir build              # produces libmylib.a
git tag v1.0.0            # versions come from tags

In the package that uses it:

[dependencies.mylib]
version = ">=1.0.0"
url = "local:/home/jane/ymir/mylib"
gyllir build              # resolves .deps/mylib, builds it, then builds this package

Your sources then use the modules of mylib as if they were part of the project.
