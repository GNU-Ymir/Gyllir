How a build works

What Gyllir does between gyllir build and the artifact appearing — useful when a rebuild does too much, too little, or fails in a way the compiler message alone does not explain.

The pipeline

  1. Read the manifest. The whole gyllir.toml is validated first; a bad entry stops the build before anything is compiled.
  2. Order the targets. Selected targets, plus every target they link, transitively, sorted so a target is always built after the ones it links.
  3. For each target: resolve its dependencies (clone/symlink, check out, build recursively), which yields the include paths and archives it builds against.
  4. Run the pre-build commands (post = false).
  5. Compile the changed modules to YIL bytecode, in parallel, then assemble every YIL file of the target into one object.
  6. Compile the C sources, if the target declares any.
  7. Finalize: link the executable, or write the library archive.
  8. Run the post-build commands (post = true).

Where the sources come from

Everything under a target's source-dir with a .yr extension is compiled, recursively. One of those files is the root module, the entry point of the package tree:

CaseRoot module
package-root declared<source-dir>/<package-root>.yr. It must exist — no fallback.
Package with no [targets.*], executablesrc/main.yr
Package with no [targets.*], librarysrc/__lib__.yr
Declared target<source-dir>/<target name>.yr

A module that is compiled but not reachable from the root module produces warning: source module <file> not attached to package. It contributes nothing to the artifact — usually it means a mod declaration is missing somewhere up the tree.

The build cache

Every intermediate file lives under .target/, one directory per target, one sub-directory per kind of build:

.target/
├── tmp/                       shared scratch space, emptied as it is used
└── <target>/
    ├── debug/                 gyllir build
    │   ├── yils/              one .yil bytecode file per module
    │   ├── *.deps             which modules each module depends on
    │   ├── c-objs/            objects compiled from c-sources
    │   └── <output>.a         every module, assembled into one object
    ├── release/               gyllir build --release
    ├── unit_debug/            gyllir test
    ├── unit_release/          gyllir test --release
    ├── test/                  the compiled test/ tree
    └── doc/                   <output>.doc.json, the input of the HTML generator

Debug and release results never overwrite each other, so switching modes does not force a full rebuild of the other one.

Incremental rebuilds

For each module Gyllir keeps a .deps file listing what that module depends on, and a .yil bytecode file. A module is recompiled when its source is newer than its cached result, or when something it depends on has been recompiled. The surviving YIL files are then assembled into the target's object, and only that step is repeated when nothing else changed.

Deleting a source file is handled too: modules that no longer exist are pruned from the cache (Removing obsolete module …) and the target is relinked without them.

If the cache ever gets out of step with reality, gyllir clean is the reset button — it only removes generated files.

Compiler options

Gyllir builds the compiler command line in this order:

  1. The root module, and -c -fPIC, plus the internal bookkeeping options (-fdump-deps, -fmodule, -fyil).
  2. -funittest for a test build.
  3. -fv when -v was given.
  4. -I <path> for every dependency and linked target.
  5. -O3 for --release, -g otherwise.
  6. Last, the target's flags — so they win over everything Gyllir picked.

At link time, the archives of dependencies and linked targets are added, then -l<name> for each entry of libraries, then the C objects. Duplicate paths are removed, so a diamond in the dependency graph does not put the same archive on the line twice.

Compilation is parallel: modules are split across -j N threads, defaulting to the number of processors.

<output> is the target's output key, defaulting to the target name — which for a single-target package is the package name.

Troubleshooting

no root module, create src/main.yr, or name another one with 'package-root'

The target has no entry point where Gyllir looks. Either create that file, or point package-root at the module you meant. See Where the sources come from for the exact rule per case.

undefined reference to 'main' at link time

The executable was rooted at a module that does not define main — typically a file named after the package was picked up while your entry point sits elsewhere. Set package-root to the module that defines main.

compiler 'gyc' could not be run

The compiler is not installed, or not on PATH. Check gyc --version, or fix the compiler key. Gyllir tells this apart from a genuine compilation failure so you are not sent looking for a bug in your code.

warning: source module … not attached to package

The module is not reachable from the root module. Nothing it contains ends up in the artifact.

A change is not picked up

Run with -v to see exactly which command lines are issued, and gyllir clean to drop the cache entirely.
