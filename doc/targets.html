Targets

A target is one artifact — an executable, a static library or a shared library — built from one source tree. A package builds as many as it declares.

Every package has targets

A package that declares no [targets.*] table still has exactly one target, synthesized from its top-level keys and named after the package. So gyllir build on a plain package builds one target called myapp, producing ./myapp. You do not have to think about targets until you want a second artifact.

To build several, declare them explicitly. Each [targets.<name>] table is self-contained: a target inherits nothing from the package, which is why declaring a target table forbids the artifact keys at the top level.

name = "myapp"
license = "MIT"
description = "A library and the CLI that uses it"
version = "0.1.0"

[targets.mylib]
type = "library"

[targets.cli]
type = "executable"
targets = ["mylib"]
output = "myapp"

This builds ./libmylib.a and ./myapp, in that order.

The root module of a declared target

A declared target roots at <source-dir>/<name>.yr — the file named after the target — unless it declares package-root. It does not fall back to main.yr or __lib__.yr; only the target synthesized for a package that declares none does that.

[targets.cli]
source-dir = "src/cli"     # sources under src/cli/
package-root = "main"      # rooted at src/cli/main.yr

Two targets can share one source-dir as long as they root at different modules, or each can have its own directory. Every .yr file under a target's source-dir is compiled for that target, so separate directories are usually what you want when the two artifacts have little in common.

A package-root naming a file that does not exist is an error, and the message names both the module Gyllir looked for and the key that decides where it looks.

Linking targets together

targets = [...] lists the targets of the same package this one links against. The listed targets are built first — their root modules go on the include path and their archives on the link line — and this holds transitively.

[targets.core]
type = "library"

[targets.plugins]
type = "library"
targets = ["core"]

[targets.cli]
targets = ["core", "plugins"]

Gyllir orders the build itself, so the declaration order in the file does not matter. A target that links itself, links a target the package does not declare, or takes part in a cycle is rejected before anything is compiled. Building or testing one target automatically builds the targets it links, even when the command names only that one target.

Selecting dependencies per target

Dependencies are declared once for the whole package, and each target picks the ones it needs:

[dependencies.midgard]
version = "*"
url = "git:git@github.com:GNU-Ymir/midgard.git"

[dependencies.somelib]
version = ">=1.0.0"
url = "git:https://github.com/example/somelib"

[targets.mylib]
type = "library"
dependencies = ["midgard"]

[targets.cli]
targets = ["mylib"]
dependencies = ["midgard", "somelib"]

A declared target links exactly what it lists. Omitting dependencies — or writing an empty array — links no dependency at all, not all of them. The single target synthesized for a package that declares no target table has no such list to write, so it keeps linking everything the package declares.

A target that links another target does not automatically inherit its dependency selection at the manifest level, but it does get everything that target already put on the link line, so the artifacts still resolve.

Version identifiers

version turns on the cte if __pragma!has_version(<ident>) (and #if <ident>) blocks of the sources, per target: each entry is passed to the compiler as -fversion=<ident>. Two targets can build the same sources with different code compiled in.

[targets.cli]
package-root = "main"
version = ["WITH_CLI", "NO_COLOR"]
fn main() {
    cte if __pragma!has_version(WITH_CLI) {
        runCli();
    } else {
        runDaemon();
    }
}

Each entry has to be an identifier — letters, digits and _, not starting with a digit — since nothing else can be named by a __pragma!has_version block. The identifiers go on the compilation of the sources and on the documentation build, ahead of the target's flags; the link does not need them. Changing them drops the build cache of the target, as a module whose sources did not change would otherwise keep the blocks it was first compiled with.

version exists only in a [targets.<name>] table: at the top level of the manifest, version is the version of the package.

C sources

A target can compile C files and fold them into its artifact — for a library, they are archived into the produced lib<output>.a; for an executable, they go on its link line.

[targets.mylib]
type = "library"
c-sources = ["c/glue.c", "c/vendor/*.c", "c/deep/**/*.c"]
c-flags = ["-Ic/include", "-DWITH_GLUE=1"]

Each entry is one of three forms, all relative to the package directory:

FormMatches
c/glue.cA literal path.
c/vendor/*.cEvery .c file directly in c/vendor/, not in its sub-directories.
c/deep/**/*.cEvery .c file under c/deep/, recursively.

Object files land in .target/<target>/<kind>/c-objs/ and are recompiled only when the source is newer than the object. They are compiled with the same compiler binary as the Ymir sources, with -g or -O3 to match the build mode, and c-flags appended last.

Shared libraries

type = "shared" builds lib<output>.so, a library that a program loads at run time (dlopen) or links dynamically. It is meant for plugins: an editor that opens the library of the project it edits and reloads it after a rebuild, without relinking itself.

[dependencies.balder]
version = ">=1.0.0"
url = "git:https://github.com/example/balder"

[targets.game]
type = "shared"
source-dir = "src/game"
dependencies = ["balder"]
host-provided = ["balder"]

[targets.editor]
source-dir = "src/editor"
dependencies = ["balder"]
exports = true

What the library leaves to its host. The program loading a plugin already holds the std lib, and often more: the engine the plugin is written against. If the plugin carried its own copy, it would get a second runtime, with a second garbage collector, second globals and second type infos. So a shared library never links the std lib, and host-provided names the dependencies (or targets of the same package) it compiles against without linking them. Their symbols stay undefined in the .so until the host loading it resolves them. A name in host-provided has to be one of the target's dependencies or targets. The std lib does not have to be listed, and listing it is an error.

A host exporting its symbols. An executable links only the members of an archive that its own code uses, and keeps its symbols out of its dynamic table, so a plugin would find neither. exports = true links it -rdynamic, with the archives of its dependencies and of the std lib taken whole, so that every symbol a plugin may look for is there.

How it is linked. The modules are already compiled -fPIC. The library is linked with -shared, its c-sources, its libraries as -l, -Wl,-soname,lib<output>.so and -Wl,-Bsymbolic, which binds the library's references to its own symbols rather than to a host symbol of the same name. A static library it links and does not leave to the host is linked in.

Linking it. A target can list a shared target in targets, and a package can name a dependency's shared target in link-targets. Without link-targets, only the dependency's static libraries are linked. Whatever links a shared library also links what it left to its host, and gets an $ORIGIN-relative rpath to the library's directory, so gyllir run and a direct run both find it as long as the two keep their relative places.

Testing it. The unit tests of a shared target are an executable, as for any other target. They link everything, the host-provided dependencies and the std lib included.

A library and its host share one runtime. The collector scans the globals of every loaded library, and the tags of a library register when it is opened. A Ymir host opens a library with etc::dl's SharedLibrary (from the std release carrying MID-187) and looks up its extern (C) functions by name. Two things to know:

  • A library constructing a class of its host (copy SomeHostClass()) needs a gyc whose -fPIC code reaches the vtables of the host through the GOT (GYC-40). Older releases fail at link time with an R_X86_64_PC32 relocation.
  • Nothing that points into a library may outlive it: its functions, and its live objects (whose vtables are its code), can no longer be used once it is closed.

Working with several targets

gyllir build              # every target, in dependency order
gyllir build cli          # cli, and the targets it links
gyllir test               # tests every target that did not opt out
gyllir test mylib         # tests only mylib
gyllir run cli -- --help  # runs the cli target, forwards --help
gyllir doc                # one site per target, under __doc/<target>/

gyllir run is the one command that needs a target name whenever the package declares more than one — it will not pick for you.
